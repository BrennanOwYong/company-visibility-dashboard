# Glossary — Clean Code

**Abstract Factory** — pattern giving the application control over WHEN objects are created while hiding HOW; used for `LineItem` creation and `DayDateFactory` (Ch 11, Ch 16)
**Active Record** — DTO variant with `save`/`find`; keep business rules out of it (Ch 6)
**ARGUMENT MARSHALER** — one class per argument type behind a common interface; the Args case study's end state (Ch 14)
**Artificial Coupling** — dependency between modules that share no real relationship (G13) (Ch 17)
**Boy Scout Rule** — check the code in cleaner than you checked it out (Ch 1, Ch 15)
**BUILD-OPERATE-CHECK** — three-part test structure: build data, operate, check results (Ch 9)
**Code-sense** — trained instinct for seeing a mess and knowing the transformations that fix it (Ch 1)
**Command Query Separation** — a function does something or answers something, never both (Ch 3)
**Conceptual affinity** — code that belongs vertically close because it shares a task or naming (Ch 5)
**Cross-cutting concern** — behavior (persistence, logging, security, transactions) that spans object boundaries; handled by aspects/proxies (Ch 11)
**Dependency Injection (DI)** — an external mechanism supplies a class's dependencies; the class stays passive (Ch 11)
**Dependency Inversion Principle (DIP)** — depend on abstractions, not concrete details (Ch 10)
**Dining Philosophers** — canonical execution model for deadlock via resource contention (Ch 13)
**Domain-Specific Testing Language** — utility functions over raw APIs that make tests read as intent (Ch 9)
**DRY** — Don't Repeat Yourself; duplication is a missed abstraction (G5) (Ch 17)
**DTO (Data Transfer Object)** — public variables, no functions; translation-stage data carrier (Ch 6)
**Dual Standard** — test code may sacrifice efficiency, never cleanliness (Ch 9)
**Emergent design** — design quality produced by applying the four simple-design rules continuously (Ch 12)
**F.I.R.S.T.** — Fast, Independent, Repeatable, Self-Validating, Timely: rules for clean tests (Ch 9)
**Feature Envy** — a method more interested in another class's members than its own (G14) (Ch 17)
**Flag argument** — boolean parameter selecting behavior; proclaims the function does two things (F3) (Ch 3, Ch 17)
**Given-when-then** — test naming convention splitting setup, action, assertion (Ch 9)
**Hidden temporal coupling** — required call order that nothing enforces (G31) (Ch 15, Ch 17)
**Hybrid** — half object, half data structure; worst of both (Ch 6)
**Intention-revealing name** — a name answering why it exists, what it does, how it is used (Ch 2)
**Law of Demeter** — talk only to immediate collaborators; no navigating through returns (Ch 6)
**Learning test** — controlled experiment that probes a third-party API and later guards upgrades (Ch 8)
**LeBlanc's law** — "Later equals never" (Ch 1)
**Mental mapping** — forcing the reader to translate a name into the concept it stands for (Ch 2)
**Newspaper metaphor** — file reads top-down from headline to detail (Ch 5)
**Niladic/monadic/dyadic/triadic** — functions of 0/1/2/3 arguments; preference in that order (Ch 3)
**One Switch rule** — at most one switch per selection type, used to create polymorphic objects (G23) (Ch 3, Ch 17)
**Open/Closed Principle (OCP)** — open for extension, closed for modification (Ch 10)
**Output argument** — argument used as output; replaced by acting on `this` (F2) (Ch 3)
**POJO** — Plain Old Java Object; business logic free of framework coupling (Ch 11)
**Principle of Least Surprise** — a function or class does what its name implies (G2) (Ch 17)
**Producer-Consumer** — canonical execution model coordinating over a bound queue (Ch 13)
**Readers-Writers** — canonical execution model balancing read throughput vs writer starvation (Ch 13)
**Selector argument** — argument (bool/enum/int) selecting among behaviors (G15) (Ch 17)
**Separation of Main** — all construction in main; the app never knows how it was built (Ch 11)
**Single Responsibility Principle (SRP)** — one reason to change per class or module (Ch 10, Ch 13)
**SPECIAL CASE pattern** — object encoding a "failure" that is really a normal alternative, removing the exception path (Ch 7)
**Stepdown Rule** — each function is followed by those one abstraction level down; code reads top-to-bottom (Ch 3, Ch 5)
**Successive refinement** — write a working draft, then clean it in tiny test-protected steps (Ch 14)
**TEMPLATE METHOD** — shared skeleton in the base class, varying steps in derivatives; kills structural duplication (Ch 12)
**Three Laws of TDD** — failing test before code; minimal failing test; minimal passing code (Ch 9)
**Train wreck** — chained navigation `a.getB().getC().doX()` exposing structure (Ch 6)
**Wading** — slogging through obscure code where changes break other places (Ch 1)
